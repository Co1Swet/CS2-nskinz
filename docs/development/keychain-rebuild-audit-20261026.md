# 挂件重建路径核查（2026-10-26）

> 后续实现与验证已记录于 [挂件仅临时 Demo 重建](keychain-temporary-demo-20261026.md)。本页“尚未实现”描述对应路径核查时的状态。

## 结论与证据边界

后续挂件开发优先接入临时 Demo 的武器 Econ 属性重写；保留现有播放时替换作为已有模块的调参预览。先验证 CS2 原生初始化能否根据重写后的属性创建／更新挂件，再决定是否补充原生刷新入口。

本次完成源码审查和四份真实 Demo 的只读解析，尚未实现产品中的挂件 Demo 重写，也未验证重写属性后无挂件武器的实际渲染。不能把此结论表述为“新增挂件已经成功”。

2026-10-10 检查点中的一项假设需要纠正：客户端存在 `C_KeychainModule`，不等于 Demo 存在可修改或插入的同名网络实体。四份录制均在完整网络类表中找不到任何名称含 `keychain` 的类，但枪械实际携带挂件属性。故没有依据把“注入 KeychainModule Created／Deleted”列为本项目的必要实现步骤。

## 当前代码

- `src/Core/AppState.hpp` 的 `KeychainProfile` 保存 XUID、枪型、挂件 kit 和清除意图，尚无位置／seed 的编辑与保留策略字段。
- `src/Runtime/DemoSkinRewrite.cpp` 的 `BuildDefaultDemoSkinRewritePlan` 目前仅收集枪械／贴纸、刀、手套，不收集 `keychain_profiles`。
- Rust `RequestItem`、`Cosmetic` 及各级规则尚无挂件对象。
- `src/Cs2/Runtime.cpp` 中 Demo 挂件控制器只修改已存在的 live 模块。找不到模块时报告 existing-module-only；一般创建路径在 `demo_playing` 时跳过。
- 现有直接替换按目标 kit 写模块，并以 seed 0 判断匹配。完善时应明确“保留源 seed／位置”和“用户覆盖”的差别，不能在仅换图案时无意重置位置或花纹。

## 必须按原始位处理属性

g161 的 AK Created 记录包含 `299/300/301/302/306`。`m_iRawValue32` 的解析类型可能显示为 Float，但含义仍由属性定义决定。

例如挂件 ID 的原始 32 位整数 17，会显示为很小的次正规浮点数。重写时应保存整数 ID 的原始位，不能把它编码成浮点数 `17.0`；seed 同样需要区分数值和原始位。位置 XYZ 使用对应浮点位。验证应逐属性比较 32 位，不应仅依赖显示文本。

## 推荐实施次序

1. 在 Demo 请求中增加独立可选的挂件配置／意图。只有挂件配置时也要生成重写任务；与同枪型枪皮／贴纸合并时保留未请求的字段，不伪造涂装请求。
2. 先实现已有挂件的原位换 kit。保留源 XYZ、seed、附加属性与全部非挂件字段；清除与不修改是不同意图。
3. 对无挂件武器，研究并补齐本机 `items_game` 定义所需的属性，使用经实际武器验证的默认挂点。**不能假定 XYZ 全零就是正确默认挂点。**
4. 每个独立 Created 和 FullPacket seek 快照都应包含一致状态；后续 Update 覆盖时仍保持目标状态。复用已修复的手套验证原则，避免全局“已处理”缓存漏掉重复句柄的新快照。
5. 输出后二次解析：先验证请求属性和非目标字段保留，再执行多位置正反向 seek。已有挂件／无挂件新增分别计数和报告。
6. 游戏内先禁用该目标的实时挂件写入，以隔离验证纯 Demo 是否足以触发原生模块。检查第一人称、第三人称、暂停、跳转、掉落／拾取及换回合。
7. 仅在确认属性正确但原生初始化未触发时，研究客户端原生挂件创建／更新入口作为受控补充。不能仅取消 `demo_playing` 条件或强行启用旧工厂分配，就宣称挂点、物理、绑定、清理均正确。

## 路径选择

| 目标 | 首选路径 | 尚需验证 |
| --- | --- | --- |
| 已有挂件实时选款预览 | 保留现有播放时模块替换 | 源位置／seed 保留、可视模型刷新 |
| 最终录制／稳定重播 | 临时 Demo 持久化武器挂件属性 | 快照、seek、原生模型生成 |
| 无挂件武器新增 | 先重建物品属性并验证原生创建 | 默认挂点、原生初始化触发、各视角 |
| 原生初始化不足时 | 播放时调用经过验证的原生更新入口 | 生命周期、实体代际、失败清理 |

原始 Demo 保持不变。默认 T／CT 手套继续严格遵守现有仅临时 Demo 重建策略；本次挂件研究不改变手套策略。
